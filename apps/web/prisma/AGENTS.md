## Purpose

The PostgreSQL schema (Prisma 7) and its migration history. About 100 models and 50 enums in one `schema.prisma`; about 300 migration folders. The generated client is written to `apps/web/generated/prisma` (git-ignored, rebuilt by `prisma generate` on `postinstall`) and used through `@/utils/prisma`. Migration and connection settings are in `../prisma.config.ts`, not in the schema.

## For AI Agents

### Working In This Directory

Imports (from the repo's `.claude/skills/prisma/SKILL.md`):

- Client instance: `import prisma from "@/utils/prisma"`.
- Enums: `import { ActionType } from "@/generated/prisma/enums"`. Types: `import type { Rule } from "@/generated/prisma/client"`.
- Never import from `@prisma/client`. Enum values must not come from `@/generated/prisma/client` in client components; `scripts/check-enum-imports.js` (`pnpm check-enums`) fails CI on that, but it only checks a hard-coded list of 14 enum names (`PRISMA_ENUMS`), so add a new enum there if it will be used in client code.
- `@/utils/prisma` wraps the client with an adapter (`@prisma/adapter-pg`), field encryption for tokens and secrets (`utils/prisma-extensions.ts`, `ENCRYPTED_FIELDS`), and an audit extension (`utils/audit/prisma-extension.ts`). Do not construct a second `PrismaClient` in app code. Standalone scripts that must (see `scripts/addUsersToResend.ts`) build their own with the same adapter.
- Fields in `ENCRYPTED_FIELDS` cannot be used in `where` filters, because encryption uses a random IV. Do not add a field that is queried by value.

Changing the schema:

- Edit `schema.prisma` and add a migration folder under `migrations/` named `YYYYMMDDHHMMSS_short_snake_case_name` (compare the newest folders). Commit both the schema change and the migration together. The client is regenerated by `prisma generate` (runs on `pnpm install`); do not hand-edit `generated/`.
- The repo's Prisma skill documents imports only, not how migrations are authored. Existing migrations are small, plain SQL files, and several are hand-written (enum `ADD VALUE`, partial and concurrent indexes). Check the SQL Prisma produces before committing it.
- Create indexes on large or hot tables with `CREATE INDEX CONCURRENTLY` (optionally `IF NOT EXISTS`), as a migration containing that single statement, as in `20261019130000_index_executed_rule_updated_at` and `20261019150000_index_executed_action_draft_status`. `CONCURRENTLY` cannot run inside a transaction block with other statements.
- Partial indexes are written in the schema with `where: raw(...)` and the `partialIndexes` preview feature (see `ExecutedAction_draftStatus_createdAt_draft_idx`).
- New enum values go in with `ALTER TYPE ... ADD VALUE` (see `20261019150100_draft_status_user_edited`).
- Never edit or rename a migration that has been merged; add a new one. Applied migrations are checksummed by Prisma.
- Do not use dynamic Prisma transactions (`prisma.$transaction(async (tx) => ...)`); see the root `AGENTS.md`.

Applying migrations:

- Production, Docker, and CI use `prisma migrate deploy`: `apps/web` `build` script, `.github/workflows/test.yml` and `playwright.yml`, and `docker/scripts/migrate.sh` on container start.
- Local development: `cd apps/web && pnpm prisma:migrate:local` (deploys using `.env.local`). The cloud-dev skill says not to run bare `prisma migrate dev` because it does not load `.env.local`; `docs/contributing.mdx` still shows `pnpm prisma migrate dev` for first-time setup. E2E uses `pnpm prisma:migrate:e2e`.
- Do not run `pnpm dev` or `pnpm build` just to apply a migration (root `AGENTS.md`); `build` also runs `migrate deploy`.

### Testing Requirements

- Database behavior (constraints, `onDelete`, partial indexes, data migrations) is tested in `__tests__/db/` against a real Postgres: `pnpm --filter inbox-zero-ai test-db` after `prisma migrate deploy` (see `__tests__/db/AGENTS.md`).
- Most other tests mock `@/utils/prisma`; see `.claude/skills/testing/SKILL.md` before writing them.
- There is no test for the schema file itself. After editing it, `prisma validate` or `prisma generate` from `apps/web` catches syntax errors.

### Common Patterns

- Ids are `String @id @default(cuid())`; most models have `createdAt` and `updatedAt @updatedAt`.
- Most per-mailbox data hangs off `EmailAccount` through an `emailAccountId` column with `onDelete: Cascade` (the `Rule` model shows the shape); check neighbouring models for the matching index.
- Index names are explicit when long (`map: "..."`) to match the SQL in migrations.
